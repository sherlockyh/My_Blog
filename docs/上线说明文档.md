## 2. 上线结论

当前项目已经具备博客主体功能和基础的安全、性能能力，并已容器化：单镜像应用（nginx + 前端静态 + NestJS 后端）配合 docker compose 一键部署（app、postgres、redis、minio）。上线前必须先完成以下两项：

1. 调整或明确后端 JSON 请求体上限；当前 `apps/server/src/main.ts` 仅允许 `32kb`，较长 Markdown 文章可能无法保存。
2. 确认生产环境 CSP、CORS、`S3_PUBLIC_BASE_URL` 与实际域名一致（见第 5 节）。

以下原先的 P0 事项已经解决：

- 数据库迁移流程：`apps/server/prisma/migrations/` 已建立初始迁移（init + pg_trgm 索引），应用容器启动时自动执行 `prisma migrate deploy`，幂等可审计。
- 上传持久化：上传图片已改存 MinIO 对象存储（`minio-data` 卷持久化），应用容器无状态，不再依赖本地 `uploads/` 目录。
- SPA 直链刷新：单镜像内 nginx 已配置 `try_files ... /index.html` history fallback。

## 4. 上线前必须处理

### 4.1 放宽文章请求体限制

当前后端在 `apps/server/src/main.ts` 使用：

```ts
app.useBodyParser('json', { limit: '32kb' });
```

文章创建和更新通过 JSON 提交，`contentZh`、`contentEn` 没有 DTO 字符长度上限。32kb 对普通短文尚可，但包含代码块、较长中文正文或双语正文时容易返回 413。

上线前建议：

- 将 JSON 上限调整为经过实际样本验证的值，例如 `1mb`；
- 同时在文章 DTO 增加合理的正文长度上限，避免无限制请求占用内存；
- 用 100KB、500KB 和超过上限的 Markdown 分别验证创建、更新和 413 响应；
- 留言、站点配置等小请求继续依赖 DTO 字段校验。

这项未完成前，不建议把后台文章发布作为上线验收通过的依据。

### 4.2 数据库迁移（已建立）

`apps/server/prisma/migrations/` 已包含两个迁移，应用容器每次启动通过 entrypoint 执行 `prisma migrate deploy`，幂等应用：

- `*_init`：全部业务表结构与基础索引；
- `*_article_search_trgm`：`pg_trgm` 扩展与文章标题/摘要 GIN 搜索索引（原 `prisma/sql/` 手工 SQL 已并入，目录已删除）。

上线前建议：

1. 在预发布环境完整跑一次容器启动，确认 `_prisma_migrations` 表记录两条迁移；
2. 若目标库过去通过 `db push` 建立过结构，先备份后在预发布库比对 schema，再决定是否需要 baseline 处理。

### 4.3 前端部署拓扑和直链刷新（单镜像已内置）

前端使用 `BrowserRouter`。单镜像内的 nginx（`docker/nginx.conf`）已配置好同域拓扑：`/api/` 反代到容器内后端、`/assets/` 长缓存、其余路径 `try_files ... /index.html` history fallback，因此直链刷新 `/articles/some-slug`、`/admin/articles` 不会 404。

若不使用单镜像而改为独立静态服务器部署，需自行实现上述 fallback 与反代规则（参考镜像内 nginx 配置即可），并保证 `client_max_body_size` 不小于上传上限。

两点 CSP/TLS 提示仍然适用：天气组件会请求 `https://api.open-meteo.com`，该域名必须保持在 CSP `connect-src` 允许范围内；生产建议在镜像前置的反向代理上统一终止 TLS、强制 HTTPS 跳转并启用 HSTS，不要只依赖应用进程返回的安全响应头。

### 4.4 上传与对象存储（已改 MinIO）

上传图片不再写应用本地目录，由后端 `StorageService` 通过 S3 兼容协议写入 MinIO（`my-blog` 桶，`uploads/*` 前缀匿名可读），浏览器直连 MinIO 的 9000 端口读取。发布时必须满足：

- `minio-data` 卷位于持久化磁盘，随数据盘一起备份；
- `S3_PUBLIC_BASE_URL` 必须配置为访客浏览器可达的 MinIO 地址（如 `http://<服务器IP或域名>:9000`），配错会导致图片全裂；
- MinIO 的 9001 Web 控制台端口应通过防火墙或反代限制访问，`MINIO_ROOT_PASSWORD` 必须是强密码；
- 换域名或迁移 MinIO 地址时，数据库中已存的完整图片 URL（`Article.cover`、`Project.cover`、`SiteConfig.avatar`）需要批量刷新，这是直连方案的固有代价；
- 历史本地 `/uploads/...` 路径的存量数据已不再提供服务，演示数据需重新上传。

## 5. 生产环境变量

后端变量通过部署平台的 Secret/Environment 管理，不提交真实值，不把生产 `.env` 打包进前端产物。compose 部署时统一放在仓库根目录 `.env`（模板见 `.env.example`）。

| 变量                                      | 是否必填 | 说明                                                                                                           |
| ----------------------------------------- | -------- | -------------------------------------------------------------------------------------------------------------- |
| `NODE_ENV`                                | 是       | 必须为 `production`                                                                                            |
| `DATABASE_URL`                            | 是       | PostgreSQL 连接串，启动时校验格式，readiness 校验连通性；compose 内由 app 服务注入                             |
| `REDIS_URL`                               | 是       | Redis 连接串，限流、缓存和浏览量依赖它；compose 内由 app 服务注入                                              |
| `JWT_SECRET`                              | 是       | 长度足够且随机；不能使用 `my-blog-jwt-secret` 或 `change-me`                                                   |
| `CORS_ORIGIN`                             | 是       | 一个或多个完整前端 URL，多个地址用英文逗号分隔，不使用 `*`                                                     |
| `PORT`                                    | 否       | 默认 `7001`（容器内固定），宿主入口端口由 `APP_PORT` 决定                                                      |
| `ADMIN_USERNAME`                          | 是       | 仅在 User 表为空时用于创建初始管理员                                                                           |
| `ADMIN_PASSWORD`                          | 是       | 初始管理员密码，禁止使用示例中的 `admin123`                                                                    |
| `APP_PORT`                                | 否       | compose 应用入口端口，默认 `8080`                                                                              |
| `MINIO_ROOT_USER`                         | 是       | MinIO 根账号（同时作为后端 S3 凭证桥接）                                                                       |
| `MINIO_ROOT_PASSWORD`                     | 是       | MinIO 根密码，至少 8 位强密码                                                                                  |
| `S3_PUBLIC_BASE_URL`                      | 是       | 浏览器直连 MinIO 的地址，部署到服务器必须改为 `http://<IP或域名>:9000`；后端 CSP 的 `img-src` 会自动追加该地址 |
| `S3_ENDPOINT` / `S3_REGION` / `S3_BUCKET` | 否       | 后端访问 MinIO 的内网地址（默认 `http://minio:9000`）、区域（默认 `us-east-1`）、桶名（默认 `my-blog`）        |
| `S3_ACCESS_KEY` / `S3_SECRET_KEY`         | 是       | 生产必填；compose 内自动桥接 `MINIO_ROOT_USER/PASSWORD`                                                        |

CSP 注意：前端 `apps/web/index.html` 的静态 CSP 已放行 `http://localhost:9000`（本地开发）；后端 `main.ts` 会按 `S3_PUBLIC_BASE_URL` 动态放行。生产若给 MinIO 配了独立 https 域名则天然被 `https:` 覆盖；若走 `http://<IP>:9000`，需同步修改 `index.html` 构建产物中的 CSP 或仅依赖后端响应头策略。

前端变量：

```ini
VITE_API_BASE=/api
```

`VITE_API_BASE` 在前端构建时写入产物。若 API 使用独立域名，必须在构建前设置完整地址，并同时检查 CORS 和 CSP。

管理员注意事项：

- `ADMIN_PASSWORD` 只在 User 表为空时创建账号，修改环境变量不会自动修改已有管理员密码；
- 首次登录后应验证后台访问和写操作，再按团队密码管理流程保存凭据；
- 当前没有多管理员、MFA 或密码修改接口，生产环境应先按单管理员、单实例后台的边界运营。

## 6. 构建与发布流程

### 6.1 容器化一键部署（推荐）

单镜像结构：根目录 `Dockerfile` 多阶段构建——builder 阶段用 pnpm workspace + turbo 构建 shared/server/web 并 `pnpm deploy` 产出后端生产依赖目录；runner 阶段基于 `node:20-alpine` + nginx，前端静态文件、nginx 配置（`docker/nginx.conf`）、后端产物与依赖合入同一镜像，由 `docker/entrypoint.sh` 依次启动 nginx、执行 `prisma migrate deploy`、前台运行 Node。

发布步骤：

```bash
cp .env.example .env   # 首次部署：按第 5 节修改真实值
pnpm docker:up         # 等价 docker compose up -d --build
```

启动顺序由 compose `depends_on: service_healthy` 保证：postgres / redis / minio 健康后才启动 app。本地开发只起基础设施用 `pnpm db:up`（postgres + redis + minio），前端 `pnpm dev:web`、后端 `pnpm dev:server`。

### 6.2 预发布或生产发布顺序

1. 确认数据库和 Redis 已备份、可连接，`minio-data` 卷可读写。
2. `git pull` 后执行 `pnpm docker:up`（构建镜像 → 启动容器 → 自动迁移）。
3. 检查 `/api/health/live` 和 `/api/health/ready` 均成功。
4. 访问 `http://<host>:${APP_PORT}` 完成前台和后台冒烟验证。
5. 观察 5xx、401、403、413、429、数据库连接和 Redis 错误日志至少一个业务观察周期。

说明：单镜像内 nginx 已承担静态托管、`/api` 反代、history fallback 与 gzip；若部署在自有 nginx/K8s 之后，注意不要重复配置 body size 限制（镜像内已设 `client_max_body_size 10m`）。

## 7. 健康检查与验收

### 7.1 服务健康检查

```bash
curl -fsS https://blog.example.com/api/health/live
curl -fsS https://blog.example.com/api/health/ready
```

成功响应外层结构为：

```json
{
  "code": 0,
  "data": { "ok": true },
  "message": "ok"
}
```

`live` 只判断进程是否存活；`ready` 会访问 PostgreSQL 和 Redis。负载均衡应使用 `live` 作为存活检查，使用 `ready` 作为接流量检查。

### 7.2 前台验收

- 首页、关于我、文章列表、文章详情、归档、分类、标签、项目、资源、留言板均能打开；
- 直接访问并刷新 `/articles/{slug}`、`/admin`、`/admin/articles` 不返回 404；
- 中文/英文切换正常，亮色/暗色切换正常；
- 文章列表搜索、标签筛选、分页和文章详情浏览量正常；
- 天气接口失败时页面主体仍可用；
- 站点头像等图片从 MinIO 直连地址（`http://<host>:9000/my-blog/uploads/...`）正常加载，浏览器控制台无 CSP 拦截报错；
- 桌面端和移动端无横向溢出，浏览器控制台无新增错误；
- 检查 HTML 标题、分享卡片和搜索引擎摘要是否符合上线预期。

### 7.3 后台验收

- 使用生产管理员账号登录，错误密码被拒绝，连续快速登录触发 429；
- 文章创建、编辑、发布、下线、删除均正常，至少验证一篇超过 32KB 的 Markdown 文章；
- 项目、资源、留言管理和站点配置/个人资料保存正常；
- PNG/JPG/WebP 上传成功，SVG、非图片扩展名和超过 5MB 的文件被拒绝；
- 上传返回的图片 URL 是 MinIO 直连地址，MinIO 控制台（9001）可见对应对象；刷新页面和重启应用容器后图片仍可访问（`minio-data` 卷持久化）；
- 写操作后能在 `AuditLog` 查到对应动作；
- 未登录访问后台 API 返回 401，不能通过前端隐藏按钮绕过后端认证。

### 7.4 数据验收

- 迁移前后核心表记录数一致；
- 随机抽查文章正文、标签、状态、发布时间和封面 URL；
- 检查 `AuditLog`、文章组合索引和 pg_trgm 索引；
- 访问文章后 Redis 计数变化，定时刷库后 PostgreSQL `viewCount` 正确；
- 执行一次 PostgreSQL 备份并在隔离库恢复验证；
- 重启 Redis 后，公开页面仍能从数据库降级读取，限流接口按设计 fail closed。

## 8. 回滚方案

### 8.1 应用版本回滚

1. 保留上一版本前端静态文件、后端构建产物和对应依赖锁文件。
2. 发现前端问题时，将静态目录切回上一版本并清理 CDN 缓存。
3. 发现后端问题时，停止当前进程，恢复上一版本 `apps/server/dist` 后重新启动。
4. 回滚后重新检查 `/api/health/ready`、前台文章详情和后台登录。

### 8.2 数据库回滚

数据库 migration 不建议直接执行反向破坏性操作。发布前必须有备份；发现字段或数据异常时：

- 优先停止写入并保留错误日志；
- 判断是否可用向前修复 migration；
- 只有确认备份时间点和数据损失范围后，才恢复备份或切换到恢复库；
- 回滚完成后重新执行健康检查、文章读取、后台写入和审计验证。

`pg_trgm` 索引或扩展创建失败时，先保留 schema migration 结果，单独处理补充 SQL，不要为了回滚搜索索引而回退业务表结构。

### 8.3 上传文件回滚

应用版本回滚不会自动回滚 `uploads/`。上传目录必须独立于应用发布目录；若文件误删，只能从上传目录备份恢复。发布和清理脚本不得删除该目录。

## 9. 上线后建议优化

以下项目不一定阻断首发，但建议尽快排期：

1. SEO：为首页、列表页和文章详情增加页面级 `title`、`description`、Open Graph、canonical 和 sitemap；如果搜索流量重要，再评估 SSR/SSG。
2. 可观测性：增加请求 ID、结构化访问日志、错误追踪、接口耗时和数据库/Redis 指标，重点监控 5xx、413、429 和上传失败。
3. 自动化验收：补充登录、文章 CRUD、留言限流、SVG 拒绝、上传持久化和健康检查的集成测试或 E2E 测试。当前仓库未发现 test/spec 文件，CI 目前主要验证编译和构建。
4. 管理员安全：增加密码修改、管理员账号轮换、MFA 或至少增加后台访问网络限制。
5. 存储扩展：图片数量或实例数增长后切换 S3/OSS，并补充 CDN、图片压缩和缩略图。
6. 数据缓存：根据访问量为首页聚合数据增加缓存和失效策略，避免每次首页请求都读取多张表。

同时满足以下条件，才建议将状态标记为“可上线”：

- P0 四项已完成并有预发布验证记录；
- `pnpm typecheck` 和 `pnpm build` 通过；
- 数据库 migration、pg_trgm SQL 和备份恢复均验证通过；
- 前端所有直链刷新通过，CSP/CORS 与域名一致；
- 管理员登录、文章发布、上传、留言和健康检查通过；
- 已准备上一版本应用包、数据库备份和上传目录备份；
- 已确定发布、监控和回滚负责人。
