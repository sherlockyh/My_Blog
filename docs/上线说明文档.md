# Code with Joy 博客上线说明

> 最后核对：2026-09-27。本文只说明生产部署；本地开发、业务流程和代码结构见文末关联文档。

## 1. 目标与部署结构

目标是：服务器拉取代码后，执行一个脚本，自动完成构建、数据库迁移、启动和健康检查。

生产部署使用 `docker-compose.prod.yml`，不拆微服务、不引入 Kubernetes。服务职责如下：

| 服务        | 类型       | 作用                                     |
| ----------- | ---------- | ---------------------------------------- |
| `postgres`  | 常驻容器   | PostgreSQL 业务数据库                    |
| `redis`     | 常驻容器   | 缓存、限流、浏览量计数                   |
| `minio`     | 常驻容器   | 图片、头像、封面等对象存储               |
| `migration` | 一次性容器 | 执行 `prisma migrate deploy`，成功后退出 |
| `server`    | 常驻容器   | NestJS API，监听容器内 `7001`            |
| `nginx`     | 常驻容器   | 托管 React 静态文件，并反代 API/上传文件 |

对外只暴露 Nginx 的宿主机端口，默认是 `8080`。PostgreSQL、Redis、MinIO 和 NestJS 只在 Compose 内部网络访问，不映射宿主机端口。

请求链路：

```text
浏览器 → nginx:80
       ├─ /api/      → server:7001
       ├─ /uploads/  → minio:9000/my-blog/uploads/
       └─ 其他路径   → React 静态文件，支持 SPA 刷新
```

## 2. 服务器前置条件

服务器需要具备：

- Git，并且项目目录已经关联可拉取的 `origin` 仓库；
- Docker Engine 和 `docker compose` 插件；
- `curl`；
- 可用的 `8080` 端口，或在生产配置中修改 `APP_PORT`；
- 当前部署分支默认是 `main`，脚本会拒绝在脏工作区或错误分支上自动拉取。

首次部署示例：

```bash
cd /opt
# 按实际仓库地址替换下面的 URL
# git clone <仓库地址> my-blog
cd /opt/my-blog
```

## 3. 生产配置

在项目根目录创建只存在于服务器上的 `.env.production`：

```bash
cp .env.production.example .env.production
vim .env.production
```

至少填写并确认以下配置：

```ini
APP_PORT=8080
CORS_ORIGIN=https://你的域名

POSTGRES_USER=blog
POSTGRES_PASSWORD=随机强密码
POSTGRES_DB=my_blog

JWT_SECRET=长度足够的随机密钥
ADMIN_USERNAME=admin
ADMIN_PASSWORD=管理员强密码

MINIO_ROOT_USER=MinIO管理账号
MINIO_ROOT_PASSWORD=MinIO强密码
S3_REGION=us-east-1
S3_BUCKET=my-blog
S3_ACCESS_KEY=应用访问账号
S3_SECRET_KEY=应用访问密码
S3_PUBLIC_BASE_URL=
```

注意：

- 不得使用模板中的 `replace-with-*`、`change-me`、`admin123` 等默认值；`deploy.sh` 会主动拒绝默认或模板密码；
- `CORS_ORIGIN` 填浏览器实际访问来源，多个来源用逗号分隔；
- Compose 内部连接必须使用服务名：数据库用 `postgres`，Redis 用 `redis`，MinIO 用 `minio`；不要填 `localhost`；
- `.env.production` 已加入 `.gitignore`，不要提交生产密钥；
- `S3_PUBLIC_BASE_URL` 留空时，上传接口返回 `/uploads/...` 相对路径，由 Nginx 同源反代；只有使用 CDN 或对象存储直链时才配置它；
- 当前版本的 `S3_ACCESS_KEY/S3_SECRET_KEY` 需要具备当前上传流程所需的 bucket 能力，后续再拆分最小权限账号。

## 4. 一键部署

给脚本增加执行权限：

```bash
chmod +x scripts/deploy.sh scripts/health-check.sh
```

默认从 `main` 分支拉取并部署：

```bash
./scripts/deploy.sh
```

部署脚本按以下顺序执行：

1. 检查 `.env.production`、Docker、Compose、Git、curl 和必填变量；
2. 拒绝默认密码；
3. 检查当前分支和工作区，避免覆盖服务器本地修改；
4. `git fetch` + `git pull --ff-only` 拉取代码；
5. 使用当前 Git commit 短 SHA 作为镜像版本标签；
6. 校验生产 Compose 配置；
7. 构建 `server` 和 `nginx` 两个生产镜像；
8. 启动 PostgreSQL、Redis、MinIO，并等待健康检查；
9. 单独执行 `migration`，迁移成功后才继续；
10. 启动 NestJS 和 Nginx，并等待容器健康；
11. 请求 Nginx、NestJS live 和 ready 接口，全部通过才返回成功。

如果部署分支不是 `main`，显式传入分支名：

```bash
./scripts/deploy.sh release
```

不要用下面的本地 Compose 命令代替生产脚本：

```bash
# 不建议作为生产发布入口：它使用本地 docker-compose.yml，无法保证生产迁移和服务启动顺序
# docker compose up -d --build
```

## 5. 部署验收与运维命令

部署成功后检查服务状态：

```bash
docker compose --env-file .env.production -f docker-compose.prod.yml ps
```

查看全部生产日志：

```bash
docker compose --env-file .env.production -f docker-compose.prod.yml logs -f
```

查看关键服务日志：

```bash
docker compose --env-file .env.production -f docker-compose.prod.yml logs --tail=200 migration server nginx
```

手动执行健康检查：

```bash
./scripts/health-check.sh
```

健康接口含义：

```text
GET /healthz              Nginx 入口存活
GET /api/health/live      NestJS 进程存活，不访问外部依赖
GET /api/health/ready     PostgreSQL、Redis、MinIO 均可用
```

示例：

```bash
curl -fsS http://127.0.0.1:8080/healthz
curl -fsS http://127.0.0.1:8080/api/health/live
curl -fsS http://127.0.0.1:8080/api/health/ready
```

正式域名接入 HTTPS 后，应使用域名进行同样的验收：

```bash
curl -fsS https://你的域名/api/health/live
curl -fsS https://你的域名/api/health/ready
```

## 6. 上线必测功能

- 首页、文章列表、文章详情可访问；
- 直接刷新文章详情、`/admin`、`/admin/articles` 不返回 404；
- 管理员可以登录，错误密码被拒绝；
- 文章可以新增、编辑、发布和下线；
- 项目、资源、留言和首页配置可以保存；
- 图片上传成功后，刷新页面仍可访问 `/uploads/...`；
- 未登录访问后台 API 返回 `401`；
- 快速重复登录可以触发 `429`；
- 中英文、亮暗主题和移动端布局正常；
- 浏览器控制台没有新增 CSP 或接口错误。

同时确认：

- `migration` 日志没有错误；
- PostgreSQL 核心表和管理员记录存在；
- MinIO `my-blog/uploads/` 中存在上传对象；
- 后台写操作产生 `AuditLog`；
- 访问文章后浏览量正常变化；
- Redis 重启后，公开页面仍能读取数据库核心数据。

## 7. 数据、迁移和备份

- 生产迁移目录是 `apps/server/prisma/migrations/`；
- 生产只执行 `prisma migrate deploy`，不要用 `prisma db push` 替代；
- `postgres` 的 `pgdata`、MinIO 的 `minio-data` 是持久化数据卷，必须纳入备份范围；
- Redis 的 `redisdata` 主要用于缓存和计数，是否备份按业务恢复要求决定；
- 不要在生产环境执行 `pnpm db:seed`；
- 管理员环境变量只在 `User` 表为空时用于创建账号，修改环境变量不会覆盖已有管理员密码；
- 当前后端 JSON 请求体上限为 `32kb`，定义在 `apps/server/src/main.ts`；Nginx 的 `10m` 上传限制不能绕过后端 JSON 限制。

## 8. 常见故障

| 现象                 | 优先检查                                                                |
| -------------------- | ----------------------------------------------------------------------- |
| 脚本提示缺少环境变量 | `.env.production` 是否从模板复制，变量名是否拼写正确                    |
| 脚本拒绝默认密码     | 修改 JWT、PostgreSQL、MinIO 和管理员密码，不能保留模板值                |
| 脚本拒绝拉取         | 当前分支必须与部署分支一致，工作区不能有未提交修改                      |
| `migration` 失败     | PostgreSQL 健康状态、`DATABASE_URL` 拼接值、迁移日志                    |
| `server` 启动失败    | `docker compose ... logs --tail=200 server`，重点检查配置校验和依赖连接 |
| `ready` 失败         | PostgreSQL、Redis、MinIO 的健康状态和日志；`live` 成功不代表依赖可用    |
| 图片打不开           | 返回路径、`my-blog` 桶、MinIO 对象、Nginx `/uploads/` 代理和 CSP        |
| 后台页面刷新 404     | Nginx SPA fallback 和前端路由                                           |
| 登录后接口 401       | `JWT_SECRET`、CORS 来源、浏览器 Token 和请求基地址                      |
| 端口被占用           | `APP_PORT` 或服务器已有进程；不要把内部服务端口暴露到公网               |

## 9. 应用回滚

1. 保留失败版本的容器日志和 Git commit；
2. 将服务器工作区切换到上一份已验证的提交，并确保分支与部署参数一致；
3. 重新执行 `./scripts/deploy.sh`；
4. 检查 `/healthz`、`/api/health/live`、`/api/health/ready`、首页和后台登录；
5. 数据库迁移不自动回滚，禁止未经验证直接执行破坏性反向迁移；优先通过新的向前迁移修复；
6. 应用回滚不会回滚 MinIO 文件，不能因为回滚应用而删除 `minio-data` 数据卷。

## 10. 当前边界

当前方案按单应用入口、单台服务器的基础生产部署设计。多实例扩容、CDN、完整监控告警、MFA、细粒度权限和 Kubernetes 不属于本次上线范围。
