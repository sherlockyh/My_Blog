# Code with Joy 博客上线说明

## 1. 文档信息

- 适用项目：`My_Blog`
- 当前版本：`0.1.0`
- 文档日期：2026-09-01
- 适用环境：生产环境或预发布环境
- 技术栈：Vite + React 前端，NestJS + Prisma 后端，PostgreSQL，Redis

本文基于当前仓库代码、配置和现有项目文档整理。类型检查和构建通过，只能说明代码可以编译，不能替代数据库迁移、依赖连通性、反向代理和真实页面验收。

## 2. 上线结论

当前项目已经具备博客主体功能和基础的安全、性能能力，但还不能直接判定为生产就绪。上线前必须先完成以下四项：

1. 解决并在预发布环境实际验证数据库结构部署；当前仓库没有 Prisma migration 历史，且此前 `prisma db push` 出现过 `Schema engine error`。
2. 调整或明确后端 JSON 请求体上限；当前 `apps/server/src/main.ts` 仅允许 `32kb`，较长 Markdown 文章可能无法保存。
3. 确认前端静态服务支持 `BrowserRouter` 的 history fallback，并确认 CSP、CORS 与实际域名一致。
4. 为 `uploads/` 配置持久化磁盘和备份；当前上传实现是单实例本地文件存储。

AI 对话在生产环境也是启动必需项：`NODE_ENV=production` 时，`AI_API_KEY` 和 `AI_MODEL` 缺一不可。没有配置时后端会在启动校验阶段失败，而不是使用本地降级回复。

## 4. 上线前必须处理

### 4.1 放宽文章请求体限制

当前后端在 `apps/server/src/main.ts` 使用：

```ts
app.useBodyParser('json', { limit: '32kb' });
```

文章创建和更新通过 JSON 提交，`contentZh`、`contentEn` 没有 DTO 字符长度上限。32kb 对普通短文尚可，但包含代码块、较长中文正文或双语正文时容易返回 413。

上线前建议：

- 将 JSON 上限调整为经过实际样本验证的值，例如 `1mb`；
- 同时在文章 DTO 增加合理的正文长度上限，避免无限制请求占用内存；
- 用 100KB、500KB 和超过上限的 Markdown 分别验证创建、更新和 413 响应；
- 留言、站点配置、AI 对话等小请求继续依赖 DTO 字段校验。

这项未完成前，不建议把后台文章发布作为上线验收通过的依据。

### 4.2 建立生产数据库迁移流程

当前仓库有 `schema.prisma` 和一份需要手工执行的 PostgreSQL SQL，但没有 `apps/server/prisma/migrations/` 目录。生产环境不能把 `db push` 当作正式发布流程。

建议按以下顺序处理：

1. 先对现有数据库执行完整备份，并记录当前表、索引和数据量。
2. 在与生产版本一致的预发布数据库上生成并验证初始 migration。
3. 将 migration 文件提交到仓库，生产使用 `pnpm db:migrate:deploy`。
4. migration 成功后，再执行 `apps/server/prisma/sql/2026-08-23-backend-hardening.sql`，创建 `pg_trgm` 扩展和文章标题/摘要搜索索引。
5. 检查 `Article`、`AuditLog`、文章排序组合索引和搜索索引均已存在。
6. 记录迁移版本、执行时间、数据库备份位置和回滚负责人。

如果目标数据库过去通过 `db push` 或手工 SQL 建立，不能直接在非空生产库上盲目生成初始 migration。应先在备份副本上比对 schema，再确定 baseline 方案。此前本项目曾出现 Prisma `Schema engine error`，必须在预发布环境先复现、定位并验证通过后再进入生产。

### 4.3 确认前端部署拓扑和直链刷新

前端使用 `BrowserRouter`。静态服务器收到 `/articles/some-slug` 或 `/admin/articles` 的首次请求时，必须回退到 `index.html`，否则浏览器刷新或分享直链会返回 404。

推荐前后端同域部署：

- 前端构建时保持 `VITE_API_BASE=/api`；
- `/api/` 反向代理到 NestJS；
- `/uploads/` 反向代理到 NestJS 或由同一持久化目录直接提供；
- 其他路径执行 `try_files $uri $uri/ /index.html`。

Nginx 配置示例：

```nginx
server {
    listen 443 ssl;
    server_name blog.example.com;

    root /srv/my-blog/web;

    location /api/ {
        proxy_pass http://127.0.0.1:7001;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /uploads/ {
        proxy_pass http://127.0.0.1:7001;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

当前前端 `index.html` 和后端 `main.ts` 都包含 CSP，`connect-src` 中仍有本地开发地址。天气组件还会请求 `https://api.open-meteo.com`，该域名也必须加入两处 CSP；否则天气请求会被浏览器拦截，组件可能只表现为静默隐藏。如果生产采用前后端分域，还必须同步加入真实 API 域名；如果采用上面的同域方案，前端 API 使用相对路径即可。

反向代理应负责 TLS 证书、HTTP 到 HTTPS 跳转，并在确认全站 HTTPS 正常后启用 HSTS。不要只依赖应用进程当前返回的安全响应头来代替完整的 HTTPS 配置。

### 4.4 配置上传文件持久化

当前 `StorageService` 将文件写入 `join(process.cwd(), 'uploads')`，并通过 `/uploads` 公开访问。发布时必须满足：

- `uploads/` 位于不会随应用版本替换而丢失的持久化磁盘或卷；
- 新实例启动后能访问历史图片；
- 对上传目录执行定期备份，并在发布前验证恢复；
- 限制目录写权限，应用进程只拥有必要权限；
- 当前采用本地存储时先保持单实例，避免多实例之间文件不一致。

对象存储尚未纳入当前实现。后续切换 S3/OSS 时，应保持接口返回的 `/uploads/...` 或等价公开 URL 契约，并补做历史图片迁移和回滚方案。

## 5. 生产环境变量

后端变量通过部署平台的 Secret/Environment 管理，不提交真实值，不把生产 `.env` 打包进前端产物。

| 变量 | 是否必填 | 说明 |
| --- | --- | --- |
| `NODE_ENV` | 是 | 必须为 `production` |
| `DATABASE_URL` | 是 | PostgreSQL 连接串，启动时校验格式，readiness 校验连通性 |
| `REDIS_URL` | 是 | Redis 连接串，限流、缓存和浏览量依赖它 |
| `JWT_SECRET` | 是 | 长度足够且随机；不能使用 `my-blog-jwt-secret` 或 `change-me` |
| `CORS_ORIGIN` | 是 | 一个或多个完整前端 URL，多个地址用英文逗号分隔，不使用 `*` |
| `PORT` | 否 | 默认 `7001`，需与反向代理或容器端口一致 |
| `ADMIN_USERNAME` | 是 | 仅在 User 表为空时用于创建初始管理员 |
| `ADMIN_PASSWORD` | 是 | 初始管理员密码，禁止使用示例中的 `admin123` |
| `AI_API_BASE_URL` | 否 | OpenAI 兼容接口地址，默认 `https://api.openai.com/v1` |
| `AI_API_KEY` | 是 | 生产环境必填，只能放后端 |
| `AI_MODEL` | 是 | 生产环境必填 |
| `AI_TIMEOUT_MS` | 否 | 1 到 60000 毫秒，默认 15000 |

前端变量：

```ini
VITE_API_BASE=/api
```

`VITE_API_BASE` 在前端构建时写入产物。若 API 使用独立域名，必须在构建前设置完整地址，并同时检查 CORS 和 CSP。

管理员注意事项：

- `ADMIN_PASSWORD` 只在 User 表为空时创建账号，修改环境变量不会自动修改已有管理员密码；
- 首次登录后应验证后台访问和写操作，再按团队密码管理流程保存凭据；
- 当前没有多管理员、MFA 或密码修改接口，生产环境应先按单管理员、单实例后台的边界运营。

## 6. 构建与发布流程

### 6.1 发布前构建

在与 CI 一致的 Node 20 和 pnpm 9.15.9 环境执行：

```bash
pnpm install --frozen-lockfile
pnpm --filter @my-blog/server prisma:generate
pnpm --filter @my-blog/shared build
pnpm typecheck
pnpm build
```

构建结果：

- 前端：`apps/web/dist`
- 后端：`apps/server/dist`
- Prisma Client：由 `prisma:generate` 生成

### 6.2 预发布或生产发布顺序

1. 确认数据库和 Redis 已备份、可连接，确认 `uploads/` 持久化卷可读写。
2. 发布后端依赖和构建产物。
3. 执行 `pnpm db:migrate:deploy`。
4. 执行 pg_trgm 补充 SQL，并检查执行结果。
5. 启动后端进程：`node apps/server/dist/main.js`。
6. 检查 `/api/health/live` 和 `/api/health/ready` 均成功。
7. 发布 `apps/web/dist` 到静态服务器，启用 history fallback。
8. 访问前台和后台完成冒烟验证。
9. 观察 5xx、401、403、413、429、数据库连接、Redis 和 AI 供应商错误日志至少一个业务观察周期。

当前仓库只提供 PostgreSQL 和 Redis 的 `docker-compose.yml`，没有应用 Dockerfile 或完整生产编排文件。因此生产部署需要由现有服务器、CI/CD、进程管理器或容器平台补充应用运行方式，不能直接把开发用 compose 当作完整生产方案。

## 7. 健康检查与验收

### 7.1 服务健康检查

```bash
curl -fsS https://blog.example.com/api/health/live
curl -fsS https://blog.example.com/api/health/ready
```

成功响应外层结构为：

```json
{
  "code": 0,
  "data": { "ok": true },
  "message": "ok"
}
```

`live` 只判断进程是否存活；`ready` 会访问 PostgreSQL 和 Redis。负载均衡应使用 `live` 作为存活检查，使用 `ready` 作为接流量检查。

### 7.2 前台验收

- 首页、关于我、文章列表、文章详情、归档、分类、标签、项目、资源、留言板均能打开；
- 直接访问并刷新 `/articles/{slug}`、`/admin`、`/admin/articles` 不返回 404；
- 中文/英文切换正常，亮色/暗色切换正常；
- 文章列表搜索、标签筛选、分页和文章详情浏览量正常；
- 天气接口失败时页面主体仍可用；
- 首页 AI 对话能发送消息，生产环境实际验证真实模型调用和超时降级；
- 桌面端和移动端无横向溢出，浏览器控制台无新增错误；
- 检查 HTML 标题、分享卡片和搜索引擎摘要是否符合上线预期。

### 7.3 后台验收

- 使用生产管理员账号登录，错误密码被拒绝，连续快速登录触发 429；
- 文章创建、编辑、发布、下线、删除均正常，至少验证一篇超过 32KB 的 Markdown 文章；
- 项目、资源、留言管理和站点配置/个人资料保存正常；
- PNG/JPG/WebP 上传成功，SVG、非图片扩展名和超过 5MB 的文件被拒绝；
- 上传后刷新页面，图片 URL 仍可访问；重启应用后历史图片仍可访问；
- 写操作后能在 `AuditLog` 查到对应动作；
- 未登录访问后台 API 返回 401，不能通过前端隐藏按钮绕过后端认证。

### 7.4 数据验收

- 迁移前后核心表记录数一致；
- 随机抽查文章正文、标签、状态、发布时间和封面 URL；
- 检查 `AuditLog`、文章组合索引和 pg_trgm 索引；
- 访问文章后 Redis 计数变化，定时刷库后 PostgreSQL `viewCount` 正确；
- 执行一次 PostgreSQL 备份并在隔离库恢复验证；
- 重启 Redis 后，公开页面仍能从数据库降级读取，限流接口按设计 fail closed。

## 8. 回滚方案

### 8.1 应用版本回滚

1. 保留上一版本前端静态文件、后端构建产物和对应依赖锁文件。
2. 发现前端问题时，将静态目录切回上一版本并清理 CDN 缓存。
3. 发现后端问题时，停止当前进程，恢复上一版本 `apps/server/dist` 后重新启动。
4. 回滚后重新检查 `/api/health/ready`、前台文章详情和后台登录。

### 8.2 数据库回滚

数据库 migration 不建议直接执行反向破坏性操作。发布前必须有备份；发现字段或数据异常时：

- 优先停止写入并保留错误日志；
- 判断是否可用向前修复 migration；
- 只有确认备份时间点和数据损失范围后，才恢复备份或切换到恢复库；
- 回滚完成后重新执行健康检查、文章读取、后台写入和审计验证。

`pg_trgm` 索引或扩展创建失败时，先保留 schema migration 结果，单独处理补充 SQL，不要为了回滚搜索索引而回退业务表结构。

### 8.3 上传文件回滚

应用版本回滚不会自动回滚 `uploads/`。上传目录必须独立于应用发布目录；若文件误删，只能从上传目录备份恢复。发布和清理脚本不得删除该目录。

## 9. 上线后建议优化

以下项目不一定阻断首发，但建议尽快排期：

1. SEO：为首页、列表页和文章详情增加页面级 `title`、`description`、Open Graph、canonical 和 sitemap；如果搜索流量重要，再评估 SSR/SSG。
2. 可观测性：增加请求 ID、结构化访问日志、错误追踪、接口耗时和数据库/Redis 指标，重点监控 5xx、413、429、AI 降级和上传失败。
3. 自动化验收：补充登录、文章 CRUD、留言限流、SVG 拒绝、上传持久化、健康检查和 AI fallback 的集成测试或 E2E 测试。当前仓库未发现 test/spec 文件，CI 目前主要验证编译和构建。
4. 管理员安全：增加密码修改、管理员账号轮换、MFA 或至少增加后台访问网络限制。
5. 存储扩展：图片数量或实例数增长后切换 S3/OSS，并补充 CDN、图片压缩和缩略图。
6. 数据缓存：根据访问量为首页聚合数据增加缓存和失效策略，避免每次首页请求都读取多张表。

## 11. 最终放行标准

同时满足以下条件，才建议将状态标记为“可上线”：

- P0 四项已完成并有预发布验证记录；
- `pnpm typecheck` 和 `pnpm build` 通过；
- 数据库 migration、pg_trgm SQL 和备份恢复均验证通过；
- 前端所有直链刷新通过，CSP/CORS 与域名一致；
- 管理员登录、文章发布、上传、留言、AI 对话和健康检查通过；
- 已准备上一版本应用包、数据库备份和上传目录备份；
- 已确定发布、监控和回滚负责人。
