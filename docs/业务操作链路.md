# 业务操作链路

> 本文描述用户操作从前端到后端、数据库、Redis 或 MinIO 的流转。接口统一带 `/api` 前缀；后端成功响应统一为 `{ code, data, message }`。

## 1. 通用请求链

```text
React 页面
  → apps/web/src/services
  → Axios http 封装
  → /api/...
  → NestJS Controller
  → DTO / Guard / Service
  → Prisma、Redis 或 MinIO
  → 统一响应
  → 页面更新状态
```

前端请求封装位于：

```text
apps/web/src/services/http.ts
```

它会：

- 从 Zustand auth store 读取 token；
- 自动添加 `Authorization: Bearer <token>`；
- 自动解包后端成功响应的 `data`；
- 后台页面收到非登录接口 `401` 时，清理登录状态并跳转 `/admin/login`。

## 2. 管理员登录

入口：

```text
后台登录页 → POST /api/auth/login
```

处理链路：

```text
1. RateLimitGuard 按 IP 限制 60 秒最多 5 次
2. AuthService 查询 User
3. bcrypt 比较密码哈希
4. JwtService 签发 JWT
5. 前端保存 token
6. 后续后台请求携带 Authorization
```

代码入口：

```text
apps/web/src/services/auth.ts
apps/server/src/modules/auth/controllers/auth.controller.ts
apps/server/src/modules/auth/auth.service.ts
```

注意：

- 登录失败的 `401` 只提示账号或密码错误，不会触发后台页面强制跳转；
- `User` 表为空时，后端模块初始化会创建初始管理员；
- 修改 `ADMIN_USERNAME` 或 `ADMIN_PASSWORD` 不会覆盖已有用户。

## 3. 公开文章浏览

### 3.1 文章列表

```text
GET /api/articles
```

后端只查询已发布文章，可按关键词、标签和分页参数筛选，并从 Redis 合并实时浏览量。

相关入口：

```text
apps/server/src/modules/article/controllers/article.controller.ts
apps/server/src/modules/article/article.service.ts
```

### 3.2 文章详情和浏览量

```text
GET /api/articles/:slug
```

处理链路：

```text
1. 按 slug 查询文章
2. 草稿或不存在时返回 404
3. Redis 设置 article + IP 的 60 秒去重键
4. 首次计数时用 PostgreSQL viewCount 初始化 Redis counter
5. Redis counter +1
6. 将文章 ID 加入 dirty 集合
7. 返回文章详情和当前浏览量
```

浏览量相关键：

```text
counter:article:{id}
dedup:article:{id}:{ip}
dirty:article_views
```

持久化规则：

- 定时任务每 5 分钟批量写回 PostgreSQL；
- NestJS 退出时再尝试刷库；
- Redis 读取失败时，文章详情降级使用数据库中的 `viewCount`；
- 同一 IP 在 60 秒内不会重复增加浏览量。

## 4. 后台文章管理

后台接口统一受 `JwtGuard` 保护：

```text
GET    /api/admin/articles
GET    /api/admin/articles/:id
POST   /api/admin/articles
PUT    /api/admin/articles/:id
DELETE /api/admin/articles/:id
```

新增或编辑链路：

```text
后台文章表单
  → article service
  → JwtGuard 校验 JWT
  → ValidationPipe 校验 DTO
  → ArticleService
  → Prisma 写入 Article
  → AuditInterceptor 记录 AuditLog
  → 返回文章数据
```

新增、编辑、删除都会记录审计动作。文章数据变化时，相关缓存会按服务逻辑失效。

文章正文通过 JSON 提交，目前后端 `main.ts` 的 JSON 请求体上限是 `32kb`；超过限制会在进入业务 Service 前返回 `413`。

## 5. 图片上传

接口：

```text
POST /api/admin/upload
```

处理链路：

```text
1. 前端使用 multipart/form-data 上传字段 file
2. JwtGuard 校验管理员身份
3. RateLimitGuard 按 IP 限制 60 秒最多 20 次
4. Multer 使用内存存储接收文件
5. 校验扩展名、MIME 类型和 5MB 大小限制
6. StorageService 生成时间戳 + UUID 文件名
7. 通过 S3 SDK 写入 MinIO 的 my-blog/uploads/
8. 返回 /uploads/xxx.ext
```

允许类型：

```text
PNG、JPG、JPEG、GIF、WebP
```

默认访问链路：

```text
开发环境：浏览器 /uploads/... → Vite → localhost:9000/my-blog/uploads/...
生产环境：浏览器 /uploads/... → Nginx → minio:9000/my-blog/uploads/...
```

数据库通常只保存相对路径，不保存本地文件内容。

相关入口：

```text
apps/web/src/services/upload.ts
apps/server/src/modules/upload/controllers/upload.controller.ts
apps/server/src/modules/upload/storage.service.ts
```

## 6. 首页配置和个人资料

公开读取：

```text
GET /api/site
```

后台修改：

```text
PUT /api/admin/site-config
PUT /api/admin/profile
```

读取链路：

```text
1. 先读取 Redis 站点缓存
2. 缓存不存在时并行查询 SiteConfig 和 Profile
3. 补充默认值并组合为公开 SiteDTO
4. 写入 Redis，缓存 10 分钟
5. 返回首页配置和个人资料
```

保存链路：

```text
1. JwtGuard 校验管理员
2. 读取当前配置并合并提交字段
3. Prisma upsert 写入 PostgreSQL
4. 删除 Redis 站点缓存
5. AuditInterceptor 记录审计
```

下一次公开读取会重新从数据库加载最新配置。

## 7. 项目、资源和留言

项目和资源的后台接口都遵循相同模式：

```text
GET    /api/admin/projects
POST   /api/admin/projects
PUT    /api/admin/projects/:id
DELETE /api/admin/projects/:id

GET    /api/admin/resources
POST   /api/admin/resources
PUT    /api/admin/resources/:id
DELETE /api/admin/resources/:id
```

共同链路：

```text
JwtGuard → DTO 校验 → Service → Prisma → AuditLog → 统一响应
```

留言的公开接口：

```text
GET  /api/messages
POST /api/messages
```

公开留言创建有 Redis 限流：

```text
同一 IP 60 秒最多 3 次
```

后台留言管理：

```text
GET    /api/admin/messages
DELETE /api/admin/messages/:id
```

## 8. 健康检查

```text
GET /api/health/live
GET /api/health/ready
```

区别：

- `live` 不访问外部依赖，只判断 NestJS 进程是否存活；
- `ready` 执行 PostgreSQL `SELECT 1` 和 Redis `PING`；
- `live` 成功不代表数据库和 Redis 已经可用。

## 9. 审计和限流是怎么生效的

两者都在 `AppModule` 中全局注册，但不是所有路由都会自动执行具体逻辑。

### 限流

只有加了 `@RateLimit(...)` 的路由才限流：

```text
登录：auth-login，60 秒 5 次
留言：message-create，60 秒 3 次
上传：admin-upload，60 秒 20 次
```

Redis 异常时，限流守卫会抛错，避免高风险接口在没有保护的情况下继续运行。

### 审计

只有加了 `@AuditAction(...)` 的写操作才记录 `AuditLog`。日志通常包含：

```text
操作人、用户名、动作、目标类型、目标 ID、详情、IP、时间
```

## 10. 排查顺序

遇到业务问题时，按实际链路定位，不要只看前端页面：

```text
1. 浏览器 Network：确认请求 URL、方法、请求体、状态码
2. 前端 services：确认是否正确调用 /api 和是否携带 JWT
3. NestJS Controller：确认路由、Guard、DTO
4. Service：确认业务分支和数据库操作
5. PostgreSQL：确认最终数据
6. Redis：确认缓存、限流或浏览量键
7. MinIO：确认上传对象和访问路径
8. AuditLog：确认后台写操作是否实际执行
```
